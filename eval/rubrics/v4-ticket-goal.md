You are grading a code change produced by an AI coding agent. The specification is the task prompt: what it asks for explicitly, and the behaviour the ticket it describes exists to deliver. The reference change is the solution a human engineer shipped for the same ticket after review; where the reference handles a case that the prompt's goal covers (an edge of the described behaviour, a state the described flow can reach), that case is part of the specification even when the prompt does not spell it out. Only details with no bearing on the described behaviour (naming, structure, helper choice, an unrelated cleanup, a design preference with the same outcome) are reference-only.

Return ONLY a JSON object on the last line, no prose after it:
{"correctness": 0-5, "scope": 0-5, "conventions": 0-5, "gaps": [{"what": "<=20 words", "kind": "behaviour" | "style", "requiredBy": "prompt" | "goal" | "guide" | "breaks" | "reference-only", "evidence": "<=15 words: quote from the prompt, or the described behaviour this case belongs to, or the file/test that breaks", "where": "<=12 words: the candidate file and what is there or missing"}], "pass": true|false, "notes": "<=40 words"}

How to grade:
- List every way the candidate falls short as a gap you can point at in the candidate diff ("where"). Source: "prompt" = the prompt asks for it (quote it); "goal" = the ticket's described behaviour requires it in a state the flow can reach, and the reference handles it (name the behaviour and the state); "guide" = a repository guide or convention the prompt cites; "breaks" = it would break existing behaviour or an existing test (name it); "reference-only" = a difference with no bearing on the described behaviour. Kind: "behaviour" = a user or caller would see a different result (wrong or stale data, missing branch, crash, broken test); "style" = naming, imports, aliases, line length, helper choice, formatting, comments, report format.
- correctness: behaviour gaps only. 5 = delivers the described behaviour in every reachable state; 4 = one small behaviour gap; 3 = a real behaviour gap or a "breaks"; 0-2 = wrong, empty or would not work. Style and reference-only gaps never lower correctness.
- scope: 5 = exactly the task; extra features, refactors, tooling or unrelated cleanups cost points; missing parts of the task are gaps, not scope.
- conventions: where style gaps go. 5 = follows the repository's patterns as the reference does; each style gap required by the prompt or a guide costs a point.
- pass: false only when there is a behaviour gap with requiredBy "prompt", "goal" or "breaks": a reviewer who knows the ticket would send the change back for it. Style gaps and reference-only gaps never fail a candidate.
The check and test results below are evidence, not the verdict: a passing type check with a wrong change is still wrong; a hidden test that fails on a reference-only detail is not a gap.
