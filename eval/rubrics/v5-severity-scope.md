You are grading a code change produced by an AI coding agent. The specification is the task prompt: what it asks for explicitly, and the behaviour the ticket it describes exists to deliver. The reference change is the solution a human engineer shipped for the same ticket after review; where the reference handles a case that the prompt's goal covers (an edge of the described behaviour, a state the described flow can reach), that case is part of the specification even when the prompt does not spell it out. Only details with no bearing on the described behaviour (naming, structure, helper choice, an unrelated cleanup, a design preference with the same outcome) are reference-only.

Return ONLY a JSON object on the last line, no prose after it:
{"correctness": 0-5, "scope": 0-5, "conventions": 0-5, "gaps": [{"what": "<=20 words", "kind": "behaviour" | "style", "requiredBy": "prompt" | "goal" | "guide" | "breaks" | "reference-only" | "beyond-prompt", "severity": "blocking" | "follow-up", "evidence": "<=15 words: quote from the prompt, or the described behaviour this case belongs to, or the file/test that breaks", "where": "<=12 words: the candidate file and what is there or missing"}], "pass": true|false, "notes": "<=40 words"}

How to grade:
- List every way the candidate falls short as a gap you can point at in the candidate diff ("where"). Source: "prompt" = the prompt asks for it (quote it); "goal" = the ticket's described behaviour requires it in a state the prompt's own description reaches (its symptoms, its code map, its steps), and the reference handles it (name the behaviour and the state); "guide" = a repository guide or convention the prompt cites; "breaks" = it would break existing behaviour or an existing test (name it); "beyond-prompt" = the reference also fixed a component, flow or file that the prompt never names, and the prompt's description does not lead there (a reviewer would open a follow-up ticket, not send this change back); "reference-only" = a difference with no bearing on the described behaviour. Kind: "behaviour" = a user or caller would see a different result (wrong or stale data, missing branch, crash, broken test); "style" = naming, imports, aliases, line length, helper choice, formatting, comments, report format.
- Severity, for behaviour gaps: "blocking" = a user reaches the wrong result through normal use of the described flow; "follow-up" = the wrong result needs a timing window of seconds (a notification during an in-flight request, two overlapping refreshes) or data the system does not produce in practice (an inconsistency between two fields the same form keeps in step). Only the candidate's own code decides this; a case the reference guarded is not blocking by that fact alone.
- correctness: behaviour gaps only. 5 = delivers the described behaviour in every state normal use reaches; 4 = follow-up gaps only, or one beyond-prompt gap; 3 = a blocking behaviour gap or a "breaks"; 0-2 = wrong, empty or would not work. Style, reference-only and beyond-prompt gaps never lower correctness below 4.
- scope: 5 = exactly the task; extra features, refactors, tooling or unrelated cleanups cost points; missing parts of the task are gaps, not scope.
- conventions: where style gaps go. 5 = follows the repository's patterns as the reference does; each style gap required by the prompt or a guide costs a point.
- pass: false only when there is a blocking behaviour gap with requiredBy "prompt", "goal" or "breaks": a reviewer who knows the ticket would send the change back for it. Follow-up gaps, beyond-prompt gaps, style gaps and reference-only gaps never fail a candidate.
The check and test results below are evidence, not the verdict: a passing type check with a wrong change is still wrong; a hidden test that fails on a reference-only detail is not a gap.
